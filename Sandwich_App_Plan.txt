SANDWICH APP — PROJECT PLAN
Version: 1.1
Date: 2026-10-10

1. PROJECT OVERVIEW

Project name:
Sandwich

Project type:
Responsive web application built with Flutter and Dart for discovering anime and manga and tracking personal viewing/reading progress.

Reference:
The feature set defined in this plan (discovery, tracking, calendar, connections). This plan uses Flutter and Dart for the web client and proposes a web-appropriate architecture and data model.

Problem to solve:
Users may want one convenient interface to discover anime and manga, manage their personal lists, track progress, and connect supported tracking services.

Primary users:
- Anime and manga fans
- Users who want to track episodes, chapters, scores, and statuses
- Users who already use supported tracking services

Project objective:
Build a reliable, responsive web app for anime/manga discovery and tracking. Start with a small, usable MVP and add complex features only after the core workflow works.

2. SCOPE AND FEATURE PRIORITIES

MVP — BUILD FIRST
- Responsive homepage
- Browse anime and manga
- Search titles
- Basic filters, such as type, genre, and status when metadata is available
- Media detail page with title, cover, synopsis, genres, status, and available metadata
- Connect one supported tracking service
- View the user's tracking list
- Add a title to a list and update its status
- Update episode/chapter progress and score where supported
- Basic account/service connection status
- Light/dark theme
- Loading, empty, success, and error states

NEXT PRIORITY
- Support additional tracking services (AniList, MyAnimeList, Simkl), subject to API access and capabilities
- Continue-watching / continue-reading section
- Airing and release calendar
- Recommendations and related titles
- Advanced sorting and filtering for lists
- More user preferences
- Synchronization status and conflict handling
- Notifications where supported and permitted

ADVANCED / OPTIONAL
- Extension management
- Anime playback
- Manga reader
- Local media playback
- Advanced diagnostics and update management

Do not include playback, reader, or extension functionality in the MVP unless it is a firm project requirement. These features introduce additional compatibility, API, content-source, and legal considerations.

3. USER ROLES AND PERMISSIONS

Guest:
- Browse public pages
- Search and view available media information

Connected user:
- Connect or disconnect tracking services
- View and manage their own lists
- Update progress, status, and score where supported
- Configure personal preferences

Maintainer:
- Manage deployment and integration configuration
- Review application errors and operational health

A custom admin dashboard is optional. Build one only if there is a real need to manage users or server-side data.

- Home / Dashboard
  - Trending and popular titles

- Anime

  - Browse, sort, filter, and search

5. CORE USER FLOWS

Flow A — Discover a title:
Home or Browse -> Search/Filter -> Results -> Media Details

Flow B — Track a title:
Media Details -> Connect service if needed -> Add to List -> Choose status -> Save

Flow C — Update progress:
My Lists or Media Details -> Change episode/chapter progress -> Save -> Show success or error

Flow D — Manage connected services:
Account Connections -> Authorize service -> Return to app -> Confirm connection -> Load or sync supported data

Flow E — Recover from a problem:
Show a clear error -> Explain what failed -> Offer retry or reconnect -> Avoid losing unsaved user input

6. UI / UX GUIDELINES

Design direction:
- Clean, media-focused interface
- Dark theme as an option, not a requirement
- Consistent cards, typography, spacing, buttons, and form controls
- Poster grids that adapt to screen width
- Clear navigation and visible active states
- Accessible contrast, keyboard navigation, labels, and focus indicators
- Touch-friendly controls on mobile

Every data-driven page should account for:
- Loading state
- Empty state
- Error state
- Success feedback
- Unavailable or missing metadata
- Expired connection / service rate limit

Create wireframes before detailed visual styling. Define reusable design tokens for colors, typography, spacing, borders, and component sizes.

7. PROPOSED TECHNOLOGY STACK

Primary client stack:
- Flutter for the responsive web user interface
- Dart as the application programming language
- Flutter web routing (choose and standardize on a routing package such as go_router if useful)
- Flutter theming and reusable widgets for consistent design tokens and components
- Responsive layouts designed specifically for browser use, including desktop, tablet, and mobile widths

Integration layer:
- Official APIs for AniList, MyAnimeList, and Simkl where supported
- Separate service adapters so one integration can change without rewriting the entire app

Persistence and backend:
- Use browser storage only for suitable non-sensitive preferences and disposable cache. Do not treat it as secure storage for private credentials.
- Prefer the connected tracking service as the source of truth for the user’s list when the API supports it.
- Add a backend only when needed for secure OAuth/token exchange, custom accounts, server-side preferences, shared data, or controlled caching.
- If a backend database is justified, PostgreSQL is a candidate; it is not mandatory for the first milestone.
- Keep private API secrets and confidential tokens out of the Flutter web client and public assets.

Tooling and quality:
- Flutter SDK and Dart SDK
- Git and GitHub
- Figma or Excalidraw for wireframes and flows
- Flutter DevTools and browser developer tools
- Dart formatter, analyzer, Flutter tests, and integration tests
- CI checks and automated builds where practical

Implementation note: Flutter web uses the Dart/Flutter ecosystem, but a browser app still has different constraints from a native mobile or desktop app. Design navigation, responsive layouts, URL behavior, browser history, accessibility, API authentication, storage, and deployment for the web instead of copying native architecture directly.

9. API / INTEGRATION PLAN

Start with one service integration. Confirm its current API access rules, authentication requirements, rate limits, and supported list operations.

For every integration, document:
- Authorization and callback flow
- Permissions/scopes requested
- Fetch list and media details operations
- Add/update/remove list operations, if supported
- Progress and score support
- Rate-limit behavior
- Token expiry and reconnection
- Error handling and retries
- Synchronization and conflict rules

Keep integrations isolated behind a common internal interface where practical. Do not assume AniList, MyAnimeList, and Simkl support identical fields or operations.

10. SECURITY, PRIVACY, AND LEGAL CHECKLIST

- Use official authentication and authorization flows.
- Request only necessary permissions.
- Never ship private API secrets in client-side code.
- Store credentials securely; keep them out of URLs and logs.
- Validate input and authorize every private data operation.
- Handle expired tokens and revoke/disconnect flows.
- Apply rate limiting to custom backend endpoints where appropriate.
- Respect third-party API terms, copyright rules, and content-source policies.
- Provide clear error messages without exposing internal secrets.
- Review dependencies and keep them updated.
- Provide a privacy notice if collecting personal data.

Security note:
A prior review of the distributed Linux package indicated that a value named SIMKL_SECRET was present in bundled assets. Verify with the project maintainer whether it is a private credential. If it is a real private secret, rotate it and avoid including it in distributed client builds. This observation alone does not prove misuse.

14. SUCCESS CRITERIA

FIRST MILESTONE — RESPONSIVE TRACKER

The first milestone is a complete, testable responsive anime/manga tracker. It should include:
- Search and browse for anime/manga
- Media detail pages
- One account integration with a supported tracking service
- Personal lists and status changes
- Episode/chapter progress updates where supported
- Responsive layouts, loading/empty/error states, and core tests

This milestone establishes a useful product foundation before taking on playback, manga reading, extensions, or complex multi-service synchronization.

The MVP is ready for an initial release when:
- Users can browse and search media reliably.
- Media detail pages display available information clearly.
- A user can connect one supported service securely.
- The user can view their list and update supported tracking fields.
- Errors, loading states, and empty results are handled clearly.
- The interface works on mobile and desktop.
- No private credentials are exposed in client code.
- Core flows have been tested and setup/deployment instructions exist.

================================================================================
BACKEND RECOMMENDATION
================================================================================

Recommended stack:
- Frontend: Flutter Web
- Language: Dart
- Backend platform: Supabase
- Database: PostgreSQL (managed by Supabase)
- Media metadata: AniList API for the first integration
- Server-side protected operations: Supabase Edge Functions, only where needed

Why this recommendation:
Supabase provides authentication, a managed PostgreSQL database, Row Level
Security (RLS), and server-side functions without requiring us to build and
operate a complete custom backend from the beginning. PostgreSQL suits this
project because users, media entries, lists, progress, ratings, and preferences
have clear relationships and benefit from relational queries.

Initial architecture:
1. Flutter Web is the responsive client and uses Dart.
2. Supabase Auth handles registration, login, and sessions.
3. Supabase PostgreSQL stores profiles, personal lists, progress, ratings,
   linked-account metadata, and preferences.
4. The AniList API supplies public anime/manga metadata such as titles,
   descriptions, genres, and cover images.
5. Supabase Edge Functions handle operations that require private API secrets
   or trusted server-side logic. Do not put private secrets in Flutter web code.
6. Enable and test Row Level Security policies so each user can read or modify
   only their own private records.

Suggested initial tables:
- profiles: user profile and preferences
- user_media_lists: a user's media entries and list status
- progress: current episode or chapter and related progress data
- media_cache: optional cached external media metadata
- ratings: optional personal ratings and reviews
- linked_accounts: external account connection metadata; never store raw passwords
- user_settings: optional display and app preferences

MVP backend scope:
- Create an account and sign in/out.
- Search media using AniList.
- View media detail pages.
- Add anime/manga to a personal list.
- Change list status (for example: Planning, Watching/Reading, Completed, or Dropped).
- Update episode/chapter progress.
- Persist the user's data in Supabase and verify user isolation with RLS tests.

Integration and security rules:
- Keep public media metadata separate from user-specific tracking data.
- Store only the minimum external-account information required.
- Never expose Supabase service-role keys or private third-party API secrets in the
  Flutter web bundle.
- Use Edge Functions or another trusted server for protected API calls.
- Define and test RLS policies for every table containing user-specific data.
- Add rate limits, validation, and safe error handling where appropriate.

Supabase vs Firebase:
Both can support Flutter. Supabase is the recommended choice here because its
PostgreSQL relational model fits users, media, lists, progress, and statistics
well and supports flexible SQL queries. Firebase remains a viable alternative
if future requirements strongly favor Firestore's document model or its
real-time ecosystem.

Official documentation:
- Supabase Flutter: https://supabase.com/docs/reference/dart/introduction
- Supabase Row Level Security: https://supabase.com/docs/guides/database/postgres/row-level-security
- Supabase Edge Functions: https://supabase.com/docs/guides/functions
- AniList API: https://docs.anilist.co/
- Flutter Web: https://docs.flutter.dev/platform-integration/web

This is the proposed architecture for the new web app, not a claim about
any other application's backend architecture.
